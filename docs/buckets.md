# Корзины: общий счёт субъектов

Замена «Репутации субъекта» из [README](README.md). Прежняя схема держала
протекающие корзины в памяти каждой реплики: реплика видела свою долю трафика, и бот,
разложивший сто запросов по двадцати экземплярам, для каждого из них выглядел
пятью запросами. Новая схема держит счёт в одном месте и реагирует на том же
запросе, на котором порог взят, — на каком бы экземпляре он ни приземлился.

Вторая перемена — разделение труда. Капча больше **не считает запросы сама**:
у неё нет ни `charge.no_clearance`, ни весов кодов. Считают отправители канала
действий — им видно, что считать: инспектор действий на маршруте («каждый заход
на api — плюс пять процентов»), modsec по своим находкам, ip по своим спискам.
Капча — держатель корзин и ворота: принимает проценты, копит, решает. Свой
заряд у неё бывает только правилом профиля — цена провала (`on: fail`) или
показа виджета (`on: uncleared` с `next: challenge`), — и это решение
оператора, а не встроенный счёт ([ниже](#правила-по-событиям)).

## Четыре корзины

| Корзина | Ключ субъекта | Откуда ключ |
| --- | --- | --- |
| `ip` | адрес `/32` (`/128`) | из запроса |
| `sess` | идентификатор клиренса | из куки, после виджета |
| `asn_net` | анонсированный префикс, в который попал адрес | справочник кодера |
| `asn_router` | номер автономной системы целиком | справочник кодера |

Ось действия с провода выбирает корзину: `ip` → `ip`, `session` → `sess`,
`asn` → **обе** ASN-корзины — сигнал один, шкалы две: подсеть греется быстро,
вся система — медленно, и это не двойной счёт, а два вопроса к одному факту
(«эта подсеть плохая?» и «вся эта сеть плохая?»). `request` корзины не имеет —
правило приёма с ним не грузится, как и раньше.

У каждой корзины четыре параметра — два своих числа и два своих порога в
процентах заполнения (подсеть терпит больше адреса, поэтому пороги не общие):

- **`max`** — ёмкость, безразмерные единицы. Проценты чужих просьб считаются
  от неё: `note value: 5` — плюс 5% ёмкости той корзины, которую назвала ось.
- **`loss`** — потери, процентов ёмкости в секунду. Корзина протекает всегда;
  тихий субъект возвращается к нулю за `100/loss` секунд.
- **`captcha_at`** (например 60; 0 — считает, но не гонит) — корзина дошла —
  все запросы субъекта без клиренса идут на виджет: 303 на `redirect_methods`,
  отказ телом на остальных. Это делает сам инспектор своим
  ответом, списки не нужны — он и так стоит на волне.
- **`ban_at`** (например 90; 0 — выключено) — событие `bucket_ban` для правил
  профиля ([ниже](#правила-по-событиям)): обычно запись субъекта в набор
  локального слоя, и модуль режет его на краю — до шины, до инспекторов, до
  Redis. Окно, пока запись едет через секвенсор, закрыто предыдущей ступенью —
  капча уже отвечает отказом сама. Сколько субъект сидит в бане — `ttl`
  правила.

Лестница решения на запросе: клиренс (и его личная корзина) → `skip` из prior →
`when` → **корзины против `captcha_at`** → просьба `challenge`. Просьба
последняя, как и была: рекомендация не обходит собственное решение профиля.

## Сессия — личная корзина

Кука клиренса не меняется вовсе: идентификатор, подпись, срок. Меняется то,
что за ней стоит: у прошедшего виджет — своя корзина `sess:<id>` с теми же
`max`/`loss`. Общие корзины его не судят: подсеть перебанена на `captcha_at` —
он ходит спокойно (бан модуля на `ban_at` не в счёт: локальный слой режет до
разбора кук, это осознанная грубость края). Судит его личная корзина:
соседи греют её осью `session`, переполнилась — клиренс считается
недействительным, клиент решает виджет заново и получает новую куку с чистой
корзиной.

Этим умирают `reverify_at` и `reverify_after`: «получил клиренс, потом стал
ботом» теперь ловится не порогом счёта фазы по таймеру, а накоплением в личной
корзине — тем же механизмом, что у всех остальных субъектов.

## Хранение: Redis, без скриптов

Счёт лежит во внутреннем Redis контура — том же, где роастер, и отдельном от обменника
объектов; адрес процессы берут из ключа `internal` блока `redis` своего `inspector.conf`
(окружение `REDIS_INTERNAL_URL` перекрывает, без обоих — `REDIS_URL` с предупреждением при
старте, см. docs/deploy/README.md#redis). Один писатель убирает вопрос сходимости целиком:
инкремент атомарен, читатель всегда видит сумму всех экземпляров. Это
каноничная схема распределённого лимитирования (GCRA — она же в
`nginx limit_req` и redis-cell), а не своя механика.

Потери не требуют ни таймеров, ни read-modify-write. Значение хранится в
«сдвинутых» координатах:

```
stored = effective + rate*now          rate = loss/100 * max   [ед/с]
```

- заряд — чистый `INCRBYFLOAT`: атомарный и коммутативный, сто экземпляров
  пишут вперемешку без потерь обновлений;
- создание — `SET key rate*now NX` тем же pipeline: кто первый, тот задал
  точку отсчёта;
- эффективный уровень — `stored − rate*now`, считается в Go из ответа
  `INCRBYFLOAT`; Redis о потерях не знает;
- пол на нуле — `PEXPIRE effective/rate`: ключ умирает ровно в момент, когда
  корзина дотекла до нуля; отрицательных значений не существует;
- потолок — тот же `PEXPIRE`, срезанный `max/rate`: сколько бы атака ни
  налила сверху, остывание не дольше `100/loss` секунд. Выше ёмкости счёт не
  копится: экземпляр, увидевший перелив, выправляет значение обратным `SET`;
  гонка такой коррекции стоит потерянного заряда у потолка, где он уже ничего
  не решает.

На запрос — один pipeline точечных O(1)-команд по затронутым ключам; никто
никогда не читает корзину целиком. Ключ: `cap:bkt:<профиль>:<корзина>:<субъект>`.
Профиль в ключе намеренно: у разных маршрутов разные ёмкости, а несколько
сервисов капчи с одинаковым именем профиля делят корзины — и это желаемое
«все экземпляры держат счёт синхронно». Рост нагрузки — шардирование по ключу
(субъект целиком на одном шарде), не мультимастер.

Redis недоступен — экземпляр считает в своей памяти той же арифметикой
(защищает хотя бы от того, что видит сам) и возвращается на общий счёт, когда
Redis отвечает. Нового класса отказа нет: без Redis процесс и так не живёт.

## Правила приёма: три поля

```yaml
trigger:
  prior:
    - from: "*"
      accept: [challenge]        # ужесточение можно всем
    - from: action
      accept: ["*"]              # все глаголы капчи: challenge, skip, note
    - from: modsec
      accept: [note]
      codes: [MODSEC_SQLI]
```

`from` (имя или `*`), `accept` (глаголы; `"*"` — все), `codes` (пусто — любой
повод). Умерли: фильтр осей `apply` — куда падает заряд, называет сама просьба;
потолки `max_percent`/`max_value` — границы держат загрузчик отправителя
(−100…900 и ±100) и ёмкость корзины, третье число между ними ничего не
защищало. Неизменным осталось главное: послабление требует имени —
широковещательное правило годится только для `challenge`, всё остальное
(`skip`, знак `note`) от `*` не принимается.

`threshold` капча больше не принимает: счёт фазы перестал быть триггером
(`trigger.when: score` и `score_at` умерли, осталось `always | buckets |
never`), и масштабировать коэффициентом нечего. Единственная шкала — корзины,
двигают их глаголом `note`. Сырой счёт фазы капча не читает вовсе — вместе с
ним выпилен и PoW, единственный его потребитель: он доказывал вычисление, а
не человечность, наказывал слабые устройства и был бедным заменителем
распределённого счётчика, которым стали корзины. Self-hosted умолчание —
картинка.

## Справочник сетей: кодер

Локальный каталог ASN у капчи умирает. Источник — кодер гео внутри контура,
по gRPC (`geo.v1.Geo/Lookup`, адрес — `WAF_CAPTCHA_GEO_ADDR`). На адрес он
отдаёт **все** накрывающие анонсы от узкого к широкому, эффективный — тот,
чей кусок под адресом остался после вычета более узких, — первым и с самим
куском; по просьбе (`expand_asn`) — состав каждой системы целиком; и `gen` —
поколение своего снимка ([docs/geo](https://github.com/exemt/placitum-geo/blob/develop/docs/README.md)).

Резолв **синхронный**: промах — один поход в кодер в таймаут
(`WAF_CAPTCHA_GEO_TIMEOUT`, 500 мс) внутри бюджета сообщения. Модуль всё равно
ждёт инспектора до дедлайна маршрута, а «пусто на первом запросе» — это молча
несостоявшийся бан. Стоит промах один локальный RTT, один раз на диапазон.
Кто ходит: ключи корзин по системам — на каждом запросе, где такие корзины
включены; записи `write: net | net_all | asn` — в момент записи. Кодер нужен записи и
молчит — запрос отвечает `error` (`CAPTCHA_GEO_UNAVAILABLE`), решает
`waf_exception` маршрута; ключам корзин молчащий кодер даёт пустоту, корзины
по системам этот запрос не считают, и это видно в журнале.

Кэш — два яруса, оба без лимитов и без сроков: данные кодера меняются
поколениями, и единственная причина забыть — новый `gen`. Диапазоны:
неизменяемый отсортированный массив **эффективных кусков** (не анонсов —
кодер их уже сплющил, и узкий `/24` внутри `/9` другой системы никогда не
получит `/9`), двоичный поиск, подмена указателя на вставке. Составы систем:
карта по номеру. Отрицательный кэш по адресу — единственное, что протухает по
времени: отсутствие данных — не данные. Потолок входящего сообщения gRPC
поднят: умолчание в 4 МБ обрезало бы состав крупной системы так же молча, как
прежний `LimitReader`.

## Правила по событиям

Жёсткой механики попыток и банов нет — что делать на событиях, решают правила,
той же формы, что строки профиля адреса: «когда → кому → что сделать».

```yaml
rules:
  - on: fail                  # провалил попытку виджета
    charge: ip                # заряд своей корзины
    percent: 20               # ±% ёмкости: пять провалов -- корзина полна
  - on: pass                  # прошёл проверку
    charge: ip
    percent: -100             # обелить адрес
  - on: pass                  # прошедшие -- для быстрого пути модуля:
    list: cap_cleared         #   waf_inspect ... if $waf_request_cookies.waf_cid
    write: cid                #   not in cap_cleared
    ttl: 24h
  - on: bucket_ban            # корзина дошла до второго порога (ban_at)
    bucket: ip                # какая; пусто -- любая
    list: blacklist           # запись в набор: дальше режет модуль
    write: addr               # addr | net | net_all | asn | cid -- что писать
    ttl: 1h
  - on: bucket_ban
    bucket: asn_net
    list: blacklist
    write: net                # горячая подсеть уезжает целиком, анонсом
    ttl: 1h
  - on: bucket_captcha        # первый порог (captcha_at) -- тоже событие:
    to: modsec                # просьба соседу; пороги живут на волне,
    do: threshold             # fail и pass -- в HTTP, им просьбы недоступны
    delta: 100
  - on: cleared               # клиент предъявил действующий клиренс:
    to: counter               # человек проверен -- снять его корзину
    do: note                  # у счётчика
    apply: session
    value: -100
    counter: scraper
  - on: cleared
    to: vlai                  # и не звать классификатор на этот запрос
    do: off
  - on: cleared
    do: mark                  # метка на записи маршрута: исполняет модуль
    marker: human verified
  - on: cleared
    list: cap_seen            # cid известен и здесь: куку предъявили
    write: cid
    ttl: 1h
  - on: uncleared             # клиренса нет, что бы лестница ни решила
    to: rewrite               # дальше: соседи дальше по цепочке видят
    do: mutate                # непроверенного -- маска выдачи включена,
    group: prices             # пока виджет не пройден
    set: on
  - on: uncleared
    to: vlai                  # и классификатор зовётся только к ним
    do: active
  - on: uncleared             # цена показа виджета: бот, который его
    next: challenge           # игнорирует, копит корзину до бана; кого
    charge: ip                # капча пропустила (next: allow), не платит
    percent: 30
```

У правила ровно одно действие: заряд своей корзины (`charge` + `percent`),
запись в набор (`list` + `write` + `ttl`) либо просьба соседу (`to`/`do`/…,
форма канала действий целиком: просьбы соседям, режим вызова соседа, глаголы
записи маршрута `audit`/`archive`/`mark`/`score`; у капчи только ось запроса
— на кадрах она не стоит). Событий волны четыре — `bucket_captcha` при
`captcha_at`, `bucket_ban` при `ban_at` (прежнее имя `bucket_full` читается
как `bucket_ban` одно поколение), `cleared` — запрос клиента с действующим
клиренсом и `uncleared` — запрос клиента без него (куки нет, истекла, битая,
привязана к чужой сети, погашена, личная корзина переполнена); селектор
`bucket` есть только у порогов. `cleared` и `uncleared` — состояние и
срабатывают на каждом таком запросе: просьба канала действует на один запрос,
повторная запись в набор продлевает срок, заряд ложится снова — памяти «уже
сделано» у реплики нет. `uncleared` не смотрит, что лестница решила дальше —
пропустить клиента или показать виджет; просьба соседу с него доедет, только
если запрос пойдёт дальше: капча пропустила или стоит на маршруте в `vote`.
Где о клиенте ничего не узнали — запрос к самому виджету, отказ списка
клиренсов, обменник не отдал заголовки, — нет ни того, ни другого. `write:
cid` кладёт короткий идентификатор куки и живёт на `pass` и `cleared` — кука
известна там, где её выдали или предъявили; у `uncleared` её нет. Прежней
автоматики «в banned-набор» и жёсткой публикации прошедших больше нет: нет
правил — нет ни бана, ни списка. Петля попыток отсюда же: `fail → charge ip`
вместо мёртвых `loop.max_attempts`/`lock`.

Уточнение `next` — что лестница решила с клиентом на этом запросе: `allow`
(пропустила) или `challenge` (потребовала проверку: виджет редиректом или
телом, отказ с билетом; в наблюдении — потребовала бы); пусто — любое
решение. Оно есть у `uncleared` и у порогов корзин, где решение бывает
любым; у `cleared` оно всегда «пропустила», у `fail` и `pass` его нет вовсе.
Так назначают цену показа виджета: бот, который виджет не решает и даже не
пытается, провалов не копит — `on: fail` его не видит, — а показы копит и
доходит до `bucket_ban`; кого капча пропустила, не платит. Заряд правила
ложится после решения, поэтому порог бана под такую цену — ниже ёмкости:
следующий запрос читает уровень уже за вычетом утечки.

Этим умирают: секции `loop` (попытки, исчерпание, замок подсети) и `list`
(cleared/banned — их пишут правила), секция `pages` в панели (на каких путях
стоит капча, решает маршрут тегом profile=; в файлах загрузчик её ещё
читает), автоматический `publishBans`.

## Форма профиля

Новая секция и то, что она вытесняет:

```yaml
buckets:
  ip:        { max: 100,  loss: 1,   captcha_at: 60, ban_at: 90 }
  sess:      { max: 100,  loss: 1,   captcha_at: 60 }
  asn_net:   { max: 300,  loss: 1,   captcha_at: 70 }
  asn_router: { max: 1000, loss: 0.5, captcha_at: 80, ban_at: 95 }
```

Пороги у каждой корзины свои: `captcha_at` гонит на виджет, `ban_at` дёргает
правила `on: bucket_ban`; нулевой порог выключен — корзина считает, но не
судит. Прежние общие `buckets.captcha_at`/`ban_at` читаются одно поколение и
переливаются в корзины без своих.

Корзина без `max` выключена: не считает и не судит.

Умирают целиком: `reputation` (обе оси, `charge`, `codes`, `max`),
`trigger.reverify_at`, `trigger.reverify_after`, провайдер `pow` с ручками
`difficulty`/`difficulty_per_score`/`max_difficulty` и секцией
`provider_config.pow`, в правилах приёма — `apply`,
`max_percent`/`max_delta`/`max_value`. Одно поколение загрузчик читает мёртвые
поля и игнорирует с предупреждением — чтобы рассылка нового формата не
спотыкалась о старые файлы; потом они становятся ошибкой. `title` и `note`
остаются полями профиля, но в панели уезжают под «Дополнительно».

## Границы

| Что | Как теперь |
| --- | --- |
| Где живёт счёт | внутренний Redis контура, точечные ключи; реплики равноправны, сумма одна на всех |
| Реакция | на том же запросе: инкремент и уровень — один атомарный ответ |
| Объём | горячие субъекты последних минут; TTL вымывает остывших сам; читается только по ключу |
| Наполнение | только просьбы соседей; своих вливаний у капчи нет |
| Отказанные модулем | до капчи не доезжают и корзин не греют — считать их может только сам модуль |
| Кука | без изменений; личная корзина — запись в Redis, не поле куки |
| Чем доказывают | картинка (self-hosted умолчание) или внешний виджет; PoW выпилен вместе со счётом фазы |
